Fable quality from cheap models.

Frontier-quality coding work is not only a model choice. It is model + harness + operating discipline + verification.

Define quality Verification loop
Operating thesis 
Cheap model + strong operating layer + verification loop + escalation path
= surprisingly high-quality work at much lower cost

Do not ask a cheap model to be smarter. Give it a smarter job, better context, sharper checkpoints, and a clean way to hand off when the risk rises.

The frame

The cheap model is only one layer.

The class should teach that strong outcomes come from structure, feedback loops, and judgment that frontier agents often have baked in.

A cheaper model can do surprising work when the surrounding system supplies tools, files, command results, remembered context, tests, acceptance criteria, and rollback paths.

Behavioral quality

What "Fable 5 quality" means.

Define it behaviorally, not mystically. The goal is not to impersonate a frontier model; it is to reproduce the work habits that make its output useful.

Plans before actingTurns vague intent into an ordered path before touching files.
Keeps the goal in mindDoes not drift into attractive side quests or unrelated refactors.
Uses tools wellReads source, runs commands, gathers evidence, and lets outputs change its mind.
Verifies claimsChecks docs, code, tests, screenshots, or live behavior before reporting certainty.
Does not stop at plausibleTreats the first answer as a hypothesis until proof is available.
Reports clearlyExplains what changed, what was proven, and what risk remains.
Knows when to escalateRoutes hard reasoning, high-risk edits, or ambiguous product calls to a stronger model or human.

Operating layer

Teach the loop explicitly.

Use a per-session operating layer when the model does not reliably carry the discipline itself.

01classify

Name the task type, risk, and authority before acting.

02gather

Read the repo, docs, or tool output before inventing a solution.

03act

Make the smallest useful change that satisfies the goal.

04verify

Run the relevant command, test, visual check, or source check.

05report

Explain result, proof, and remaining risk in plain language.

Class rule

Use operating text as a per-session layer, not a permanent global default. The point is to make the model behave like a disciplined teammate for this job, then revise the layer as students see where it succeeds or fails.

Verification

Cheap models need cheap proof.

Every loop should end with evidence. The cheapest proof that actually answers the question is usually enough.

For code editsRun the narrow test, linter, build, or command that exercises the touched behavior.
For UI changesCheck the page at desktop and mobile widths, then confirm no text overlaps or scrolls sideways.
For factual claimsUse primary docs or live output, especially for model pricing, APIs, and current behavior.
For risky actionsPause for a stronger model or human review before deploy, secrets, payments, data deletion, or broad refactors.

Escalation path

Do not make the cheap model carry every risk.

Fable or Sol quality often comes from knowing when not to keep using the cheap path.

  1. Stay cheapRepetitive edits, local searches, first drafts, summaries, small tests, and low-risk scaffolds.
  2. Ask for proofAny time the answer sounds plausible but has not touched code, docs, commands, or observed behavior.
  3. Escalate the modelArchitecture changes, long-horizon debugging, ambiguous product judgment, subtle security issues, or compounding failures.
  4. Escalate to a humanProduction deployment, spend, secrets, legal or policy interpretation, and irreversible operations.

Class exercises

Practice the operating discipline.

Students should leave with a repeatable way to judge whether the system is doing real work.

Rewrite a vague requestTurn "fix this page" into a goal, constraints, done definition, verification, and report format.
Run the same task twiceCompare cheap model alone against cheap model plus operating layer and verification.
Build an escalation ruleChoose which failures require a frontier model and which require a human.
Create a proof habitMake every answer include what was verified and what was only inferred.
