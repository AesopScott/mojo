Build your first harness with Pi.

Pi is a small terminal coding agent you can understand end to end. The class goal is to turn it from "a chat that edits files" into a controlled harness with context, tools, rules, memory, verification, and a repeatable workflow.

Class promise

By the end, you should be able to describe the harness around Pi and sketch one practical harness you can build for your own workflow.

What you will learn

Learn Pi as a harness, not as magic.

An AI coding agent is only useful when the system around it controls what it can see, what it can do, how it remembers, and how its work is checked.

Outcome 1

You can name the harness parts.

Context, instructions, tools, filesystem scope, memory, approval boundaries, verification, and recovery. The model is not the whole product.

Outcome 2

You can run a controlled workflow.

You will practice a repeatable loop: orient, plan, edit, verify, summarize, preserve what matters, and avoid uncontrolled changes.

Outcome 3

You can design a first harness.

You will leave with a one-page spec for a small harness around a real task: content publishing, repo cleanup, evidence gathering, or customer follow-up.

Two-hour class path

What we will do together.

We will move from concept to example to your own first harness spec. The goal is to leave with a pattern you can repeat, not just a vocabulary list.

0:00-0:10

Frame the problem

We will separate the model, the app, the agent, and the harness. Pi gives us a small enough system to see the pieces clearly.

Key idea: Pi is not valuable only because it can type code. Pi becomes valuable when we wrap it in a workflow that controls context, tools, verification, and memory.
0:10-0:25

Map the harness parts

You will connect the seven parts: objective, context, instructions, tool boundaries, working memory, verification, and handoff.

0:25-0:45

Compare controlled and uncontrolled runs

We will compare a vague request with a controlled request so you can see why ambiguity, missing context, and unchecked edits create risk.

0:45-1:10

Turn the same task into a harnessed run

You will see how a goal, constraints, file boundaries, verification requirement, and summary format change Pi's output.

1:10-1:35

Build the first harness spec

You will choose one recurring task and fill out the worksheet: what gets loaded, what is allowed, what proof is required, and what gets saved.

1:35-1:55

Group review and upgrades

We will review a few draft harness specs and improve them by adding approval gates, narrower scope, and better verification.

1:55-2:00

Choose your next build

You will choose one small repeatable loop to try before the next session.

Live build

The first harness you can understand.

We will use a "page update harness" because it is visible, low-risk, and easy to inspect: change a page, verify it, and report exactly what changed.

Harness ingredients

  • Objective: update one page for one audience.
  • Scope: only the target file and supporting assets.
  • Rules: keep design consistent, avoid unrelated edits, preserve secrets.
  • Tools: file search, file edit, local server, browser verification.
  • Proof: screenshot, link check, no unrelated diff.
  • Memory: summarize the reusable lesson for next time.

Starter prompt

We are updating one page only: /pi/.

Goal: make the page explain what a harness is to a beginner.
Rules:
- Do not edit unrelated files.
- Use existing site patterns.
- Include a student worksheet.
- Verify the page renders and links work.

Before editing, inspect the existing site style and summarize the intended change.

Core concepts

How to think about Pi while you build.

Pi is a clear lens for understanding AI harnesses. The class is not about installing another tool. It is about learning how a small agent becomes powerful when you define the operating boundary around it.

Analogy

The model is the engine. The harness is the vehicle.

The engine can produce power, but the vehicle provides steering, brakes, dashboard, fuel rules, safety systems, and destination.

Correction

Pi does not automatically know the project.

Pi has access to the context that gets loaded. The harness decides what context is in bounds and how changes are verified.

Memorable line

A harness is judgment made repeatable.

If you can describe the decisions a careful human makes around an AI task, you can begin turning those decisions into a harness.

Student worksheet

Design your first harness.

Fill this out for one recurring task. Keep it boring and real. A boring harness that runs every week is better than an impressive example no one repeats.

1. TaskWhat repeatable AI task do you want Pi to help with?
2. InputsWhat files, notes, examples, URLs, or instructions should be loaded?
3. BoundariesWhat files, tools, actions, or decisions are out of bounds?
4. WorkflowWhat steps should happen every time before edits are made?
5. VerificationWhat proof tells you the work is correct enough to keep?
6. HandoffWhat should Pi report, save, or ask after the run?

Class close

End with one concrete next step.

The assignment is simple: pick one recurring workflow and write the harness spec before trying to automate it. Your first harness should be small enough that you can explain it in two minutes.

Suggested homework

  1. Choose one task you already repeat.
  2. Write the six-part harness spec.
  3. Run Pi once with the spec.
  4. Save what worked and what failed.
  5. Bring the failure back to the next class.
